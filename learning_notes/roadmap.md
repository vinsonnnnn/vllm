# 学习路线与完成标准

版本与环境以 [首页](README.md) 为准。章节按需推进；“继续下一章”只新增下一章、增补术语和检查记录，不重新生成已完成内容。开始下一轮先核对固定源码基线与用户改动；结束后按首页记录的授权自动提交并推送本轮改动。

## 阶段一：建立能导航的主路径（01—03）

| 章 | 核心任务 | 完成标准 |
| --- | --- | --- |
| 01 | 仓库地图、入口、运行条件 | 不靠全仓库盲搜，能定位 LLM、V1 LLMEngine、EngineCore、Scheduler、Executor、GPU Worker 和实际 Runner 分支；能解释为什么本机尚不能推理 |
| 02 | 追踪一个请求的进入、执行和返回 | 画出带通信类型的端到端链；指出 tokenization、request ID、采样、终止判断、detokenization 和最终输出的位置；分清 frontend step 与 core step |
| 03 | 数据结构和状态转换 | 区分 EngineCoreRequest、Request、SchedulerOutput、ModelRunnerOutput、EngineCoreOutput 与 RequestOutput；按一次完成或 abort 追踪对象所有者和清理 |

先不重复 Transformer 推导；用已有 nano-vLLM 知识解释模块职责，但不借用未出现的 nano-vLLM 文件或函数名。前两章只展示必要数据结构，第三章再系统展开。

## 阶段二：能解释资源和计算如何衔接（04—06）

| 章 | 核心任务 | 完成标准 |
| --- | --- | --- |
| 04 | 每轮调度、预算、加入与抢占 | 对两请求教学案例手算调度，区分请求数限制、输入 token 预算和调度 token 预算；定位扣减与状态更新；解释 continuous batching 的迭代边界 |
| 05 | 逻辑 token 到物理 KV 存储 | 跟踪分配、block pool、命中、释放；明确 Block Table 与 Slot Mapping 的不同消费方；说明 prefix cache 命中后哪些计算仍需执行 |
| 06 | Runner 输入与后端调用 | 根据配置确认 MRV2/MRV1；追踪持久请求状态到本轮输入、positions、attention metadata、KV 写入和采样输入；能找到所选模型与后端，暂不遍历全部实现 |

本版入口包括 `vllm/v1/core/sched/scheduler.py`、`kv_cache_manager.py`、`block_pool.py` 和 `vllm/v1/worker/gpu/`。第四章应核实抢占/重算的具体实现；不能直接照搬 nano-vLLM 中块管理器的所有权模型。

## 阶段三：恢复生产执行特征（07—08）

| 章 | 核心任务 | 完成标准 |
| --- | --- | --- |
| 07 | IPC、队列、异步调度 | 将前面同步案例改画为异步时间线，指出正在调度、正在执行和已回收的批次；解释 Future 不自动代表新进程，及输出回收为何影响调度状态 |
| 08 | eager 与图执行的差异 | 定位图模式选择、capture、replay、padding 和有效 token 计数；同等输入下验证输出，再讨论 CPU launch 开销、首轮成本和稳态表现 |

进程边界从第一章就标明，第七章才深入线程、序列化、共享内存的适用路径和生命周期。源码有共享内存支持不等于纯文本请求中的每条消息都走共享内存。没有 GPU 时完成源码与状态推演，运行验收保持“未完成”。

## 阶段四：把研究问题变成可复现项目（09—10）

| 章 | 核心任务 | 完成标准 |
| --- | --- | --- |
| 09 | draft→verify→accept/reject→更新 | 从支持的具体投机方法入手，定位候选 token、验证采样、接受长度、回滚/丢弃以及 KV/计数更新；列清同步与异步差异；调查已有动态预算实现 |
| 10 | 一个最小改进闭环 | 写出问题、基线、修改点、正确性约束、性能假设和消融；记录模型 revision、输入输出长度、并发、种子、缓存与 warmup 条件；留下可复现命令和原始结果 |

投机解码同时核查 `vllm/v1/spec_decode/`、`vllm/v1/sample/rejection_sampler.py` 与 `vllm/v1/worker/gpu/spec_decode/`，先确认各自对应 Runner 分支，不能跨分支拼成调用链。

验证预算可先研究“不同请求的候选长度是否应不同”，但暂不定义算法优越性。应先明确预算究竟限制 draft 计算、target 验证 token、KV 空间还是单轮延迟，以及 Scheduler 和 Runner 的契约能否表达它。

项目必须满足：

1. **可解释的正确性**：先定义输出等价或分布要求，再选择已有测试；贪心 token 一致性不能替代随机采样的分布正确性。涉及终止、取消、prefix cache、接受/拒绝时覆盖相应边界。
2. **可归因的性能**：同时观察 TTFT、后续 token 延迟、端到端延迟、吞吐和资源使用；分开低并发与高并发，固定有效输出 token 数和负载。接受率高不能单独证明加速。
3. **可复现的证据**：保存基线与修改结果、重复次数、波动、失败记录及适用条件。内核微基准与端到端结果分别报告，内核性能脚本放 `benchmarks/kernels/`。
4. **可审阅的范围**：首个实验只改一个主要决策点；先在本地形成差异和证据，再按仓库贡献规则决定是否提交。未经用户要求，本笔记阶段不改业务源码。
